# docker-devkit

## What this is

`docker-devkit` owns the Docker-stack lifecycle commands — `up`, `down`, `build`, `mirror`, `publish-compose`, `generate-score`, `docker-build-matrix`. A small, generic package that any repo shipping a compose graph can depend on to get the same bring-up/tear-down / cross-build / score-generation flow. Build and render declarations live at the root of the consumer's `docker-devkit.yaml`; the compose assembly is the `services` + `gateway` vocabulary (groups with mutually exclusive `options:` selected per invocation through `BUNDLES=` in `.env`, bare riding entries, routes, ports), and `up` derives the entire assembly — including the emitted front-door caddy and its Caddyfile — from that one declaration. The PyPI identity starts its own version tags at `0.1.0`; the terminal `stack-toolkit` distributions (≤0.1.1) are deprecation signposts pointing here, not this package's history.

The package is `docker_devkit` (src-layout under `src/docker_devkit/`); all dependencies resolve from PyPI — `bashrun` (shell-outs), `build-artifact-registry` (builds-shelf push and ORAS provisioning for CI artifacts), `packaging` (`requires` specifier parsing), `pathspec`, `pydantic`/`pydantic-settings`, `pyyaml` (score-document parsing), `strictyaml` (config loading), `typer` (CLIs) — git-source pins only in scratch branches testing unreleased changes.

Config follows the org law (home: github-actions-toolkit's `AGENTS.md`): this is a root-`docker-devkit.yaml` devkit. The schema (`config.DockerDevkitConfig`, strictyaml-loaded, `extra="forbid"` on every model) carries a required `requires` version stamp plus the orchestration keys — `repository`, `base_images`, `platforms`, `project_name`, `gateway`, `services`, `k8s`, `mirror` — and never a per-workload runtime fact (see "The deployment-surface layer"). `config.load_config` self-checks the installed docker-devkit version against `requires` and refuses loudly outside the range (the `0.0.0.dev0` dev sentinel bypasses the check, not the field).

## Release flow

github-actions-toolkit's `AGENTS.md` owns the consumer workflow contract; this repo follows it unchanged. Repo-specific facts: github-actions-toolkit is never a project dependency (docker-devkit sits inside its own dependency graph; a project-level edge is a resolver cycle), and from 1.0 on API-breaking changes ship with a manually bumped `major_minor` (pre-1.0, breaking changes ride the patch flow; patch-auto assumes additive changes).

## Mirror consumption

Consumers with docker images (placeframe, capture-tool) run `mirror` via the docker-devkit dependency — inline in their `mirror-images` job (checkout + `setup-uv` + ghcr login + `uv run mirror`), version-sourced by the consumer's `uv.lock`. The job carries `permissions: { contents: read, packages: write }` + `env: GITHUB_TOKEN` (ghcr login for `crane copy`). Pure-Python devkits have no `mirror-images` job.

## Shape

Entry points (`[project.scripts]`): `up` → `compose.py:up_app`, `down` → `compose.py:down_app`, `build` → `build_docker.py:app`, `mirror` → `mirror.py:app`, `publish-compose` → `publish_compose.py:app`, `generate-score` → `score_generate.py:app`, `docker-build-matrix` → `matrix.py:app`. All accept `--help`.

| `compose.py` | The `up` and `down` typer apps — the CLI edge only: flags, the build wiring, the mirror probe, and the handoff. `up` constructs `Assembly(root, config, dev=…)` — the one construction resolves, renders, materializes, and validates; every law lives in the `assembly.py` row — then owns a `try/finally` whose `finally` runs `assembly.cleanup()` — a failure-path guarantee only: the handoff itself execs (`bash_handoff` replaces the process), so a successful run leaves the per-run files to the OS temp dir — and hands off through `bash_handoff(compose_command(root, assembly.compose_files, …))`. `down` keys on the project, not a file list: a name-only root file (written through `assembly.write_temp_compose_file`) plus `down --remove-orphans` removes every container the project ever created (any selection, any profile) without resolving a single include — an option's `:?err` env holes cannot break an open-mode teardown. With a lock file present, `up` fail-closed probes every lock entry (`docker buildx imagetools inspect`) before bring-up — classifying stderr: only a registry 404 / manifest-unknown verdict is the not-mirrored error; unauthorized or transport failures report as probe failures carrying the underlying error text. The shell form renders only through `assembly.compose_command`, always with `--project-directory` at the invocation root and `.env` as `--env-file`, plus the lock as a second `--env-file` when it exists. |
| `assembly.py` | The resolve/render/validate stage: everything between the inputs and the docker compose invocation. `Assembly(root, config, dev=False)` is the selected assembly as one record, rendered and proven — every environment read, selection derivation, document render, temp-file materialization, and compose-backed refusal runs exactly once in the constructor, and every refusal those steps own fires there (a failure after the first temp write unlinks what was written — an invalid assembly strands nothing): the merged shell-over-`.env` view (the constructor requires `.env` — the friendly refusal — and merges shell env over file values; `parse_env_file` stays in `host.py` — the external API surface), the `BUNDLES=` selection (the constructor applies the law; the riding entries, the option→group vocabulary, per-group choices, and the declaration-order entries flatten stay constructor-internal — the record exposes no selection projections, nothing prints them), the profiles, the auth-gated `forwarded` pair (derives `FORWARDED_PROTO`/`FORWARDED_PORT` from `PUBLIC_URL`, refusing when absent — only under a selected auth option), the `includes` list in `services:` declaration order with its missing-bundle-output refusal, the shared-service-name refusal over selected local outputs, the `output_services` set (the dev overlay's filter, read from the generated artifacts), and the riding routes, ports, and selected auth route. the door does no token validation (the `protected` route flag and its `forward_auth` emission were stripped when the realm plumbing proved unownable at the consumer edge — re-protection is a bundle-shipped oauth2-proxy sidecar treaty, not door vocabulary), and the service name `door` is reserved (generate-score refuses to write a bundle defining it). `_render_caddyfile()` renders the door's Caddyfile: one caddy site on the internal `:8443`, each route a `handle` block (mutually exclusive; caddy sorts them longest-path-first, so declaration order cannot shadow — a test pins the rendering) — `handle_path` for `strip_prefix`, a bare `handle` for the `/*` catch-all, and `header_up X-Forwarded-Proto/Port` on the auth option's own route (derived from `PUBLIC_URL` exactly as the retired placeframe gateway entrypoint derived it); `raw:` route content rides verbatim under its path — the escape hatch for caddy behavior outside the dialect, a review flag rather than a feature — and the whole file rides as an inline `configs.content` with every `$` doubled (compose interpolation would otherwise eat caddy's `{$ENV}` runtime placeholders). `_render_dev_overlay()` (under `dev=True`) renders the dev overlay: every assembly-defined service whose Dockerfile declares a genuine dev stage gets `image: {repository}/{service}:dev` plus the repo-root→`/app:ro` bind, and every selected workload's `dev-toggles` pairs — parsed through `config.parse_dev_toggles`, the one spelling law — become `${NAME:-default}` environment holes (spelling validated at generation; `up --dev` consumes); overlay keys outside the selected local outputs are filtered out (a stray key would add a half-defined service), and `--dev` with no dev shape in the assembly refuses. The root renders before the overlay and the `-f` list (`compose_files`) carries root-then-overlay so the overlay overrides; both are per-run temp files unlinked by `cleanup()` on the failure paths — the constructor's own and the verbs' `finally`; a successful handoff execs, so nothing runs after it and the files ride out in the OS temp dir (the tests' handoff mocks return normally, which is why they observe cleanup where production does not). Validation — the drift-impossible teeth — runs in the constructor over `compose_files` through compose's own resolution: whenever routes or ports exist, `docker compose config --services` must list every route upstream (the selected auth option's route rides the routes list by construction — its option is a selected entry, so it needs no separate check) and every port's owning service — the dev overlay's keys are a subset of the root's resolved services, so it changes nothing the check sees; whenever profiles are selected, `docker compose config --profiles` must list them, through `assert_known_profiles`. A selected bundle output that does not exist refuses naming generate-score; two selected local outputs sharing a service name refuse at construction only (selection-relative: each artifact alone is valid; the `door`-reserved and dev-toggles spelling refusals live at generation). `compose_command(root, compose_files, *arguments)` is the one docker compose invocation spelling — `-f` per file, `--project-directory` at the root, `.env` as `--env-file`, the lock as a second `--env-file` when it exists, every dynamic interpolation shlex-quoted — shared by the constructor's validation calls and the verbs' handoffs. `write_temp_compose_file(document, prefix)` is the per-run temp writer behind `compose_files` and `down`'s name-only root. `require_compose_stack(config)` is the no-compose-stack refusal both verbs share; `require_env_file(root)` the friendly `.env` refusal; `forwarded_pair(environment)` the PUBLIC_URL derivation; `_split_names` (comma-split, strip, dedupe, drop empties) and `mapping_or_empty` (the yaml narrowing `_service_names` uses) live here. |
| `build_docker.py` | `run_build()` + the `build` command — config-driven over `documents.render_bake`; `run_build` takes root/config by injection with cwd-derivation defaults, so `up --build` passes its already-loaded pair and nothing re-derives. The lock writer runs first: one entry per `base_images` key and per chart (`{NAME}_CHART`), the mirror-prefixed declared reference with its tag resolved to a digest (`{prefix}/{path}:{tag}@sha256:…`); `@digest` declarations pass through prefixed-but-unresolved; declaration-incremental by prefix match — an unchanged declaration copies its frozen digest forward (same-tag upstream re-pushes never diff a green branch), a tag bump breaks the match and re-resolves, `--upgrade` re-resolves everything. `--lock-only` writes the lock without building (the relock path — the toolkit's lock-freshness step and the consumer flips use it; a building run with zero derived services refuses loudly naming it) and self-skips — print, exit 0, write nothing — where no lock declarations exist (no config at all, or neither `base_images` nor `k8s.charts` declared), so the toolkit's getter can run it unconditionally in any repo. `--lock-only --check` (the `uv lock --check` analog) asserts instead of writes: the relock computes in memory, a unified diff against the committed lock prints and the run exits 1 when stale, nothing touches the tree — the toolkit's freshness step runs it with zero path knowledge. `--dev` builds genuine dev stages under `{repository}/{service}:dev` — per service, so fanned variants share one dev tag — never SHA-tagged, local-only (`--dev` with `--push` or with `--lock-only` refuses). | `provisioners.py` | The provisioner authoring format and its compiler. Authored provisioner files carry `state`/`outputs`/`volumes`/`services` as real YAML mappings and `manifests` as a real list (`AuthoredProvisioner`, `extra="forbid"`) — score's string form is YAML-in-a-string that no editor highlights or linter parses, so it is generated, never authored. | `markers.py` | The authoring-marker resolvers shared by the provisioner compile pre-pass, the chart-values pre-pass, and the workload rendering pre-pass (`_rendered_workloads` resolves lock markers over each workload document — a workload's `image:` field is metadata score never substitutes resource outputs into, so a third-party image rides as `image: {lock: NAME}` and lands digest-pinned in both renderings). A marker is a single-key mapping — single-key mappings keep authored sources plain-YAML-parseable (no custom tags), which is the authoring format's lintability goal. `include: <repo-root-relative path>` inserts the file's bytes verbatim as a string scalar; `include-yaml: <path>` parses the file and inserts the structure (charts like grafana's demand mapping-shaped values); neither mode transforms content — `${VAR}` holes pass through untouched; `$`-handling is per-consumer (the compose converter doubles `$`, k8s-side inclusion never does). Paths anchor at the repo root (matching how binds reference `workloads/…`); absolute paths and `..` escapes are loud errors, as are missing files, non-string marker values, invalid or empty YAML includes, and include cycles. `include-yaml` trees resolve recursively with cycle detection; text content is never scanned for markers. Lock markers run in the same two pre-passes after include resolution (included structure can carry lock markers): `lock: NAME` substitutes the entry's full lock reference, making the lock the single digest source for k8s provisioners (which have no runtime env-file to fill compose-style `${VAR}` holes); `lock-image: NAME` expands the entry into the `registry`/`repository`/`tag`/digest fields chart values want (registry is the path minus the last component, joined back into the same reference). Charts that spell the digest field `sha` (grafana's, bare hex — its template re-adds the `sha256:` prefix) declare `lock-image: {key: NAME, digest_field: sha}`. Include resolution and lock resolution stay separate sequential passes — inclusion can introduce lock markers, and text includes stay opaque to lock scanning. Unknown entry names, non-string marker values, and malformed spec mappings are loud errors, while malformed, duplicate, and non-digest-pinned lock lines reject at lock load (`documents.parse_image_lock`, the single lock reader). `contains_marker` is the predicate the values pre-pass uses to pass marker-free files through untouched. |
| `secrets.py` | The tier-neutral secrets contract, activated by the presence of the consumer-committed `stack/secrets.yaml` (a `KEY: description` mapping — or `KEY: {description: …, mint: true}` for keys that ride the externally managed cluster Secret, which derives `{project_name}-secrets`). `SecretsDeclaration` models the file itself (string specs coerce to the mapping form, keys must be ALL_CAPS, the empty declaration rejects). After generation, each rendering's consumed keys must be a subset of the declaration (subset, not equality — pair-variance is legitimate). Compose consumption is `${ALL_CAPS}` brace holes with odd `$`-parity in the artifact (`$$`-escaped configs.content doesn't count); k8s consumption is `secretKeyRef` entries naming the derived Secret (wholesale `envFrom`/`extraEnvFrom` `secretRef`s impose no per-key constraint). The mint list artifact (`stack/generated/secrets.txt`, one key per line under a provenance comment) generates from the declaration alone, so deploy-time Secret recipes and the Pulumi sync read a generated list instead of a hand copy. |
| `matrix.py` | `docker-build-matrix` — emit the CI build leg list as a bare JSON array on stdout (the binding's getter pipes it through its `matrix` verb, which composes the envelope and guards the empty case). Legs derive from the config's service set: a union-find over the derived context edges groups dependency closures, and load-time coherence guarantees one variant set per closure, so one leg builds a whole closure group in a single bake invocation; one leg per closure × variant cell — `variant` is `common` for unfanned services and the gpu family for fanned ones, `targets` the cell's targets space-joined and sorted. The leg schema — `targets`, `variant` — is a named contract with the binding; renaming a key breaks its fanout YAML. |
| `mirror.py` | The mirror namespace's config, injection, and verbs. The `mirror` verb enumerates declarations from root `base_images` plus `k8s.charts`; the prefix comes from the `mirror:` section or `DEFAULT_MIRROR_PREFIX`. Presence is probed per reference by the exact digest consumers pull — the lock entry for images, the lock's `{NAME}_CHART` entry for charts (a declared chart without its lock entry refuses loudly naming `build --lock-only`) — via `crane digest`, then one `crane copy {ref} {prefix}/{ref}` per reference the mirror lacks; zero declared targets is a loud error; the count footer splits copied from already-present. `mirrored_ref(reference, prefix)` is the only prefix join, rejecting an already-prefixed reference (the double-prefix guard). `load_mirror_config` is the thin section reader. Crane comes from the shared pinned installer (`crane.py`). |
| `publish_compose.py` | The `publish-compose` verb — publishes the local entry compose files as OCI artifacts consumers `include: oci://` by digest (`docker compose publish`). Publishing happens iff local entries are declared — no flag, no section — and artifact names derive from root `repository` (`{repository}/{entry-or-option}`, one artifact per local leg). `--plan` prints the publish legs as a bare JSON array (`[]` with no local entries) with no registry login and no publish — the CI getter's derivation source; `--bundle` publishes one leg, a bare invocation publishes every leg sequentially. Bake substitutes `${ALL_CAPS}` holes against `compute_service_shas` tree-tags plus the image lock — unresolved vars stay holes in the artifact for the consumer's `.env`, with non-empty env stubs set only so publish's interpolation validation passes (publish embeds the file uninterpolated; `${VAR:?err}` rejects unset-or-empty). Authored `configs.content` entries ride through verbatim — their single-`$` holes are the consumer's include-time interpolation surface ($-doubling is generate-score's bind-inlining concern, not publish's). Image refs under `{repository}/` are pinned to `@sha256` digests via memoized `imagetools inspect`. Each leg publishes once under the `<sha>` tag and aliases the `<branch>` tag onto the same manifest with `crane tag` (`--branch` overrides for CI) — compose stamps wall-clock `created` per invocation, so two publishes of identical files carry different digests and the alias is the only way both tags name one digest. After each leg the verb prints one `Digest <reference> <digest>` line per pushed reference and, when `GITHUB_STEP_SUMMARY` is set, appends an artifact/sha-tag/branch-tag/digest Markdown table. Registry login reads the neutral `REGISTRY_USERNAME`/`REGISTRY_TOKEN` against the repository's host. |
| `image_refs.py` | Image-reference collection, split by source. `unpinned_references(root)` scans Dockerfile `FROM`, Dockerfile `COPY --from=` (slash-bearing captures only, so build-stage names are skipped), and yaml `image:` lines — hand-written literal refs that bypass the declaration system — across the `workloads/` and `docker/` Dockerfile trees and the `stack/score/` + `score/` source trees, and polices exactly what it finds (every slash-bearing reference must carry a tag, a digest, or a trailing `${build-arg}` suffix — consumer CIs fail on its result). `bake_base_image_refs(config)` adapts root `base_images` to `ImageReference` pairs; `version_coupling_violations(root, couplings)` (each `VersionCoupling` names a pyproject-declared version and the `VersionSite` regexes that must restate it — raw file text, or a `base_images` value read from `docker-devkit.yaml` with a plain yaml safe-load, a presence probe rather than schema consumption, so non-derivable couplings like uv `required-version` ↔ uv-base-image tag can't drift silently; the mechanism lives here, the registry in consumer repos' preflight) is unchanged. Remote digest resolution goes through `imagetools inspect`. Compose files are parsed by nothing in this package. |
| `crane.py` | The shared crane installer — the pinned go-containerregistry release binary downloaded into `/usr/local/bin` (sudo unless root) for every verb that shells out to crane (`mirror`, `publish-compose`); install always runs so the pin, not a preexisting binary, decides the version. |

## The deployment-surface layer

Everything the deployment substrate (compose, k8s) needs to know about a workload that score's container model does not carry — host publishes, restart, gpu plumbing, scale-to-zero, healthcheck adaptation, consumer-supplied file content, dev toggles — lives in the **workload file** as `outernet.internal/*` annotations. `docker-devkit.yaml` never carries a per-workload runtime fact; it is build/render orchestration only. The devkit's shipped patch templates are the annotation reader: one annotation, one template, one behavior. The templates ship as package data under `src/docker_devkit/patch_templates/` (resolved via `importlib.resources`; a packaging test asserts every shipped template resolves) and register onto the devkit's own `score-compose`/`score-k8s` init invocations — consumer repos never author or declare one. Refusal laws (enums, form validation) live in devkit code (`score_generate._validate_workload_surface` and its siblings) because templates are data and cannot refuse. Score propagates `metadata.annotations` into both renderings, so the annotations ride the committed artifacts and the templates read them from the workload source — the truth the drift gate reproduces. Adding or renaming one of these annotations changes the committed artifacts: regeneration diff expectations must always include the annotation lines.

| Annotation | Behavior |
|---|---|
| `outernet.internal/gpu` | gpu plumbing (`cuda`/`rocm`). The compose pair (`gpu-cuda.tpl`/`gpu-rocm.tpl`) registers per the rendering's `GPU_VARIANT` bundle var; `gpu-pod.tpl` registers on every k8s init (runtimeClassName `nvidia`, `nvidia.com/gpu: "1"` hardcoded). The k8s nodeSelector label stays `placeframe.io/gpu` — exactly what Pulumi labels GPU nodes with; only the annotation is org-namespaced. |
| `outernet.internal/restart` | compose `restart:` emission — presence ⇒ emission; the value must sit inside the compose restart-policy enum (`no`/`always`/`on-failure`/`unless-stopped`), anything outside refuses. |
| `outernet.internal/probe-adapter` | `python-urllib` or `bash-http`: converts the workload's `readinessProbe`, else `livenessProbe`, httpGet into a compose healthcheck (the adapter picks the exec spell the image runtime can run — python-urllib for python-based workloads shipping neither wget nor curl, bash-http spelling HTTP over `/dev/tcp` for images shipping bash and nothing else — with the interval/start_period/timeout 5s, retries 3 timing block, byte-identical fleet-wide). An httpGet probe without the annotation refuses loudly naming the workload — score-compose drops httpGet probes, and the silent drop is the failure mode the refusal kills. |
| `outernet.internal/consumer-interpolated` | comma-separated `files:` names whose binds ride un-doubled at inlining, single-`$` holes becoming the include consumer's interpolation surface (the workload spells every `$` in the file as `$$`; score's materialization un-doubles them). A name matching no declared file refuses. |
| `outernet.internal/dev-toggles` | comma-separated `NAME=default` pairs (names ALL_CAPS, defaults non-empty scalars; `config.parse_dev_toggles` is the one parser, refusing at generation; an annotation on a k8s-only workload refuses). Consumed by devkit code at `up --dev` — no template, no artifact change: the pairs become `${NAME:-default}` environment holes in the generated dev overlay, so `.env` overrides apply only under `--dev` and debug-in-prod is unrepresentable. |

The `outernet.internal/publish` annotation died: host publishes are consumer config now, declared as `ports:` under `docker-devkit.yaml`'s `services` key. A workload still carrying the annotation refuses loudly at generation naming its death.

## Compose assembly and the `BUNDLES=` selection law

`up` derives the entire assembly from the consumer's root `docker-devkit.yaml` — one materialized root compose file per run, nothing hand-authored between the config and the running stack. Under `services:`, bare entries and group-level `routes:`/`ports:` ride unconditionally; only options are selectable, through `BUNDLES=` from the merged shell-over-`.env` view (the `COMPOSE_PROFILES` precedence; the `Assembly` constructor owns the law). The selection law: `BUNDLES=` names options only — a bare entry's name refuses as unselectable; at most one option per group (naming two refuses naming the group); zero options is legal exactly when riders or routes carry the assembly (omitting the auth pick is the anonymous edge — there is no explicit `open` entry); an options-only repo with an empty selection refuses; unknown names refuse loudly listing the vocabulary.

The materialized root carries the project `name:`, the `include:` list (remote refs verbatim, local outputs by absolute path, in `services:` declaration order), the emitted door (iff any route rides), and parent-file port stanzas for every riding or selected `ports:` declaration. Compose merges parent ports into included services and honors `!reset` — a test against a version-pinned standalone compose binary pins both (the parent-over-include merge needs compose ≥ 2.40; 2.24–2.39 answer `conflicts with imported resource`). Validation runs in the `Assembly` constructor, whenever routes or ports exist, over the materialized file list (root plus dev overlay under `--dev`) through `docker compose config --services`: every route upstream (the auth option's rides the routes list by construction) and every port's owning service must resolve inside the selected assembly. A declared-but-empty compose assembly is unreachable — strictyaml refuses the empty spellings, and an options-only repo with nothing selected refuses at selection.

No `services:` section (or no config at all) → both verbs refuse loudly: a builds-only, mirror-only, or k8s-only repo has no compose stack, and there is no default-file fallback. `--compose-file` does not exist; raw `docker compose` is the pressure valve. `--dev` is opt-in — production-shaped bring-up is the default; dev mode is `.env` toggles + `build --dev` + `up --dev`.

`down` never reads the selection and never resolves an include: it materializes a name-only root and hands off `down --remove-orphans`, which removes every container labeled with the project — covering prior bring-ups under any selection and any profile, offline, with no env-hole interpolation of unselected options.

Profile-gated services are selected solely by `COMPOSE_PROFILES`; the verbs hold no built-in profile names. Gpu is not runtime vocabulary — no `--gpu` on `up`/`down`, no `{gpu}` file templating; a host that cannot run what it selected fails at container create.

## File and env conventions the commands assume

- `.env` (required by `up`/`down`, loaded through `assembly.py`) — carries `BUNDLES=` (the option selector), `COMPOSE_PROFILES`, the dev-toggle overrides under `--dev`, and whatever variables the consumer's assembly interpolates — `GATEWAY_PORT` (the door's published port), `PUBLIC_URL` (the auth edge derives the forwarded scheme/port from it), and the ports' `${…}` holes.
- `docker-devkit.lock` (repo root, committed, required exactly when `base_images` or `k8s.charts` are declared) — the declaration system's resolved pair file: one `NAME={mirror-prefixed reference}@sha256:…` entry per `base_images` key and per chart, written by `build`, never hand-authored; `up`/`down` attach it as a second `--env-file` when present. The env line format is the design, not a vestige: compose consumes it natively at the `up` handoff edge and bake consumes it as environment — a structured lock would force a per-run materialization and lose the raw-`docker compose` pressure valve.
- `workloads/images.yml` does not exist — the image manifest dissolved into the root config keys; `load_config` refuses its presence loudly (the leftover-manifest guard, the flip's permanent hygiene check).
- `.dockerignore` (where images are built locally) — allowlist that `documents.py` hashes over to compute per-service `tree-<hash>` tags. See "Docker build context" in `AGENTS-SHARED.md` for the allowlist rationale.

`build` injects the `tree-<hash>` tags of locally-built images into the environment rather than writing them anywhere; `up`/`down` do the same via `compute_service_shas`. The lock stays a pure third-party pin file — a CI invariant forbids built-image digests in the committed, reviewed lock.

## Mirror namespace

Third-party images and charts are consumed through an org-owned mirror namespace (`ghcr.io/outernet-foundation/mirror/<upstream-host>/<path>…` — `DEFAULT_MIRROR_PREFIX`, overridable via the `mirror:` section's `prefix`) instead of pulling upstream registries directly: manifests at upstream get GC'd, and an upstream yank once broke external cloners — digest pins alone don't save you when the manifest is gone. Durability for strangers beats upstream egress: strangers, CI, and prod always pull the mirror. Populating it is CI's job, single writer — engineers never push to the org namespace, and error text must never teach them to (no "run this populate command" hints).

Declarations are upstream-native and the mirror-prefixed form is derived: `base_images` values and `k8s.charts` refs spell the upstream reference, and the prefix is the single place the namespace is named. `mirrored_ref(reference, prefix)` is the only join — it injects the prefix and rejects an already-prefixed reference (the double-prefix guard: drift toward the namespace is a loud error, never a silent skip). Under the section or the default:

- `build` resolves lock digests against the upstream reference and records each entry under the derived mirror name (`NAME={prefix}/{ref}@sha256:…`). Valid because `crane copy` produces byte-identical manifests — upstream and mirror digests are the same digest; a manifest re-wrap (`docker buildx imagetools`-shaped tooling) would change the top-level digest and break lock equality. This makes declare → re-lock walkable before CI has mirrored anything; lock lines are never hand-authored.
- `up` fails closed over the lock file: it probes every lock entry (each is mirror-prefixed by construction, under the declared or default prefix — the probe is not gated on a `mirror:` section); a missing mirror image is a hard `RuntimeError`, not a warning — people ignore warnings. There is no escape flag: a missing entry means the declaring change has not been through CI's mirror job yet, and the fix is to let it run. The probe's stderr is classified before an error is reported: only a registry 404 / manifest-unknown verdict gets the not-mirrored error; an unauthorized or transport failure (stale registry credentials, network, daemon down) is reported as a probe failure carrying the underlying error text, so a host-side problem can't masquerade as unmirrored CI debt.
- The `mirror` verb (the shared pinned crane installer, then a `crane digest` presence check per declared reference — the lock's exact digest for images and charts alike — and `crane copy {ref} {prefix}/{ref}` for each one the mirror lacks) uses bashrun + plain prints — it needs nothing from any runner floor. Presence is probed by the exact digest consumers pull, so once the mirror holds a digest, upstream retention is irrelevant: upstream GC of a manifest cannot break runs for bytes the mirror already owns, and upstream is consulted only to fetch what is missing. A probe that fails for any reason falls through to `crane copy`, which stays the loud gate — probe errors are never classified. Every declared reference is a target; nothing is filtered by prefix, so a drifted declaration cannot silently mirror zero, and the footer's copied/present split keeps a zero-copy run visible.

The build-artifact-registry edge exists for the builds shelf: a `build --push` run distills bake's `--metadata-file` into a digest manifest (`target → {ref, digest, tags[]}` JSON) and pushes it through build-artifact-registry's `push_build` — one **shard** per matrix leg, tagged `sha-{full}-{key}` where the key is the sha256-8 of the leg's sorted targets (legs run in parallel, so a shared tag would be last-writer-wins; the pull side enumerates a SHA's shards and merges, and consumption only ever runs after every leg finished). The shelf root comes from the neutral `REGISTRY` environment and the SHA from the checkout HEAD (`git rev-parse HEAD`), stamping the certified PR head the release channels query back at; the keying law is stated in github-actions-toolkit's `AGENTS.md`. `docker-devkit.lock` stays in source control. ORAS CLI knowledge lives only in build-artifact-registry (org law); local builds (no `--push`) never touch the shelf.

Lifecycle stays a separate package from codegen (client generation, datamodel generation, workspace locking) because their dependency surfaces are disjoint — bundling them would force a consumer that only brings a stack up to install `sqlacodegen`, `psycopg`, `datamodel-code-generator`.
