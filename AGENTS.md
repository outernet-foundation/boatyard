# docker-devkit

## What this is

`docker-devkit` owns the Docker-stack lifecycle commands — `up`, `down`, `build`, `lock`, `tree-tags`, `mirror`, `publish-compose`, `generate-score`, `docker-build-matrix`. A small, generic package that any repo shipping a compose graph can depend on to get the same bring-up/tear-down / cross-build / score-generation flow. Build and render declarations live at the root of the consumer's `docker-devkit.yaml`; the compose assembly is the `services` + `gateway` vocabulary (groups with mutually exclusive `options:` selected per invocation through `BUNDLES=` in `.env`, bare riding entries, routes, ports), and `up` derives the entire assembly — including the emitted edge caddy and its Caddyfile — from that one declaration. The PyPI identity starts its own version tags at `0.1.0`; the terminal `stack-toolkit` distributions (≤0.1.1) are deprecation signposts pointing here, not this package's history.

There is no Python API. The devkit's contracts are exactly the verb CLI, the declaration schema (`docker-devkit.yaml` + `docker-devkit.lock`), and the committed artifact formats — nothing a consumer could only use by importing `docker_devkit`. The three-class principle holds throughout: authored facts live in the config, registry-resolved facts in the lock, tree-derived facts (the `tree-<hash>` tags) are computed on demand and never committed.

The package is `docker_devkit` (src-layout under `src/docker_devkit/`); all dependencies resolve from PyPI — `bashrun` (shell-outs), `packaging` (`requires` specifier parsing), `pathspec`, `pydantic`, `pyyaml`, `strictyaml` (config loading), `typer` (CLIs) — git-source pins only in scratch branches testing unreleased changes.

Config follows the org law (home: github-actions-toolkit's `AGENTS.md`): this is a root-`docker-devkit.yaml` devkit. The schema (`config.DockerDevkitConfig`, strictyaml-loaded, `extra="forbid"` on every model) carries a required `requires` version stamp plus the orchestration keys — `repository`, `base_images`, `variants`, `platforms`, `project_name`, `gateway`, `services`, `k8s`, `mirror_prefix` — and never a per-workload runtime fact (see "The deployment-surface layer"). `config.load_config` self-checks the installed docker-devkit version against `requires` and refuses loudly outside the range (the `0.0.0.dev0` dev sentinel bypasses the check, not the field).

## Release flow

github-actions-toolkit's `AGENTS.md` owns the consumer workflow contract; this repo follows it unchanged. Repo-specific facts: github-actions-toolkit is never a project dependency (docker-devkit sits inside its own dependency graph; a project-level edge is a resolver cycle), and from 1.0 on schema/CLI/artifact-breaking changes ship with a manually bumped `major_minor` (pre-1.0, breaking changes ride the patch flow; there is no Python API to break).

## Mirror consumption

Consumers with docker images (placeframe, capture-tool) run `mirror` via the docker-devkit dependency — inline in their `mirror-images` job (checkout + `setup-uv` + ghcr login + `uv run mirror`), version-sourced by the consumer's `uv.lock`. The job carries `permissions: { contents: read, packages: write }` + `env: GITHUB_TOKEN` (ghcr login for `crane copy`). Pure-Python devkits have no `mirror-images` job.

## Shape

Entry points (`[project.scripts]`): `up` → `verbs/up.py:app`, `down` → `verbs/down.py:app`, `build` → `verbs/build.py:app`, `lock` → `verbs/lock.py:app`, `tree-tags` → `verbs/tree_tags.py:app`, `mirror` → `verbs/mirror.py:app`, `publish-compose` → `verbs/publish.py:app`, `generate-score` → `verbs/score.py:app`, `docker-build-matrix` → `verbs/matrix.py:app`. All accept `--help`. The CLI edge lives in `verbs/` — one module per command: the app object is always `app`, the command function names the command the user types (underscore-spelled), both Typer flag suppressions always set. The package root holds the domain libraries. Model modules read root → leaves: the root record (`DockerDevkitConfig` in `config.py`, `ImageLock` in `config_lock.py`, `ComposeDocument` in `documents.py`) is the first class in the file, the types it references below it in dependency order, functions after the class block — the module entry (`load_config`, `parse_image_lock`) first, then callees below their callers, leaves last. A `RootModel` subscript quotes its forward reference (`RootModel[dict[str, "SecretKey"]]`) so the root stays first; the one forced inversion is a parent whose field default constructs the child (`Field(default_factory=…)`) — the child sits above it, because the class body evaluates eagerly. `DockerDevkitConfig` is the domain record: the schema plus the derivations multiple consumers reach ride it as member functions; a derivation with exactly one call site lives at its consumer, inlined — renders and path joins sit in the modules that run them, never on the record. Consumer modules keep pipelines plus their inlined derivations. The record carries the repo `root` as a load-injected, excluded, never-authored field (absent in synthetic configs, asserted-present at the members that need it — `Assembly` parity, subprocess-in-members included). Intra-package imports are absolute (`from docker_devkit.config import …`), per the org law.

The devkit assumes fresh consuming repos: no code anywhere handles an obsolete version of a file, a dead annotation, or a pre-flip format — a consumer carrying a past artifact gets the plain parse refusal, never a migration path or a leftover guard.

Parsing and variant resolution complete before any `ServiceBuild` is constructed — `ParsedDockerfile` is the pre-resolution parse record, each `ServiceBuild` is built once fully resolved, and `target_variants` is the single target/variant pairing source. Filesystem-gated laws at load: Dockerfile services or local entries ⇒ `repository`; `base_images` or `k8s.charts` declared ⇒ the committed `docker-devkit.lock` at the repo root is required (`LOCK_PATH`; the pairing law); every declared chart requires its values file at `stack/score/k8s/values/{chart}.yaml`; routes declared anywhere ⇒ the committed lock carries `CADDY_IMAGE` (the edge's image key, read through `image_lock()`). The record's member derivations (the Shape law above): `compose_bundles()` — the local renderables (workload-bearing options and bare entries) in declaration order, outputs root-absolute at `stack/generated/compose/compose.{name}.yaml` — the render/publish legs; `tool_requirements(target)` — the pinned-tool set a target's generation needs, with the `ToolRequirement` record; `image_lock()` — the lock read where absence is legal (the empty lock); `declared_charts` — `k8s.charts` when a `k8s:` section is declared, else the empty mapping; `mirror_prefix` — the authored override or `DEFAULT_MIRROR_PREFIX`; `service_shas()` — the tree-tag environment over the derived service builds (the sha machinery beside the model: `compute_service_shas` — a module-level global, late-bound by name: the test monkeypatch seam, never inlined into the member — and `service_sha_env`, the `{SERVICE}_SHA` naming; per-service `tree-<hash>` tags over the `.dockerignore`-allowlisted `git ls-tree HEAD`; an empty service set returns `{}` without touching git or `.dockerignore`; the workload-tree root derives as the single top-level directory containing every service, files under it belonging to no service excluded from every SHA); `score_dir_path()` is the surviving path member — the other path joins (k8s output, bundle output, chart values) inline at their consumers. `chart_lock_key(name)` stays a free naming function (a spelling law, not a field derivation; the `{SERVICE}_SHA` naming lives with the sha machinery above); `parse_dev_toggles(where, raw)` is the dev-toggles `NAME=default` spelling law (ALL_CAPS names, non-empty defaults, no duplicates), the one parser generation's validator and `up --dev`'s overlay both consume. | `config_lock.py` | The lock file's schema and parsers — the resolved-state twin of `config.py`. `ImageLock`/`ImageLockEntry` (`extra="forbid"`, one after-validator per model): `images:` mapping name → `{index, platforms: {os/arch: reference}}`, `charts:` mapping name → flat digest-pinned reference. `parse_image_lock(path)` — the only reader any lock consumer uses (path:line-numbered errors; malformed documents, duplicate keys, and non-digest-pinned entries reject at parse; the empty lock is legal). `ImageLock.require(name, subject, hint=…)` is the one "lock lacks NAME" refusal every lock consumer raises (the image entry answers by its index reference, the chart entry flat); `ImageLockEntry.recorded_digests` (the index plus every platform manifest reference) is the digest set the `up`/`mirror` probes walk. | `lock.py` | The lock engine the `lock` verb and `build`'s incremental freeze share. `relock(config, upgrade=)` computes the structured lock: per `base_images` entry, the mirror-prefixed reference resolved against upstream into the index digest plus one concrete platform-manifest digest per declared platform (crane copies are byte-identical, so the digests hold under both names); `@digest` declarations pass through prefixed-but-unresolved and record uniformly as the index and every platform entry; declaration-incremental freeze — an unchanged declaration (prefixed reference plus declared platform set) copies its frozen entry forward (same-tag upstream re-pushes never diff a green branch), a tag bump breaks the match and re-resolves, `--upgrade` re-resolves everything; the computed lock owns exactly the declared names, so orphans prune by construction. Charts freeze by the same prefix match. `render_lock` is the deterministic render: sorted names, sorted platform keys, byte-stable across machines (the empty lock renders `{}\n`). Remote digest resolution lives here: `resolve_remote_digest(reference)` is the index digest through `docker buildx imagetools inspect`; `resolve_remote_manifests(reference, platforms, subject)` is the complete resolution the lock writer consumes — the index digest plus one concrete manifest digest per declared platform, a pure function of the declarations (the writing machine's arch never participates) — yielding `UpstreamManifests`, with the platform selection inlined in it: exact `os`/`architecture` match; `unknown/unknown` and attestation-annotated entries skipped; multiple matches refuse loudly naming the entry; a platform nothing matches refuses listing the index's available platforms; and a reference that answers a manifest rather than an index has one concrete byte-stream and records uniformly as the index and every platform entry. `env_entries(lock, platform=)` is the flat `NAME=reference` projection carrying the selection law: None names the index (the build edge, where buildx resolves a multi-arch index per target platform), a platform names its concrete platform manifest (the compose edge), and a platform an entry does not record refuses loudly naming the rewrite; `compose_env_entries(lock, config, environment)` the compose-edge projection, owning the platform-selection law inlined from the record: a declared singleton selects itself, a multi-platform repo names `PLATFORM=` in `.env` (shell env overriding; a missing, empty, or undeclared value refuses loudly listing the declared platforms), and None answers only a repo declaring no platforms — never host introspection; its output is the platform manifests of the selected platform (a lock recording images against a config declaring no platforms is a desync the construction rules out); `render_env_entries` the env-grammar render the per-run `--env-file` writer emits. The read projections stay here by authored placement — projections over the lock, but every consumer (compose edges, bake assembly, score's pre-passes) reaches them through this module, not config. `run_lock` is the verb body: self-skips (print, exit 0) where no config or no lock declarations exist, so the toolkit's freshness step can run it unconditionally in any repo; `--check` asserts instead of writes — the relock computes in memory, a unified diff against the committed lock prints, and the run exits 1 when stale, nothing touching the tree — only the check lane renders the lock text, for the diff; the write lane is `write_lock(config, upgrade=upgrade)` verbatim. Compose files are parsed by nothing in this package. |
| `verbs/up.py` | The `up` typer app — the CLI edge only: flags, the build wiring, the mirror probe, and the handoff. `up` owns the run's `ExitStack` and constructs `Assembly(root, config, stack, dev=…)` inside it — the one construction resolves, renders, materializes, and validates; every law lives in the `assembly.py` row — then probes, builds, and hands off through `bash_handoff(compose_command(root, assembly.compose_files, …))`, all inside the same stack. The handoff execs (`bash_handoff` replaces the process), so a successful run never unwinds the stack and the per-run files ride out in the OS temp dir; any failure unwinds it — compose files unlinked, the lock env file printed and kept; the tests' handoff mocks return normally, which is why they observe the unwind production never runs. `up` flags: `--attached`/`-a`, `--quiet-pull`/`-q`, `--build` (requires build keys — `repository` or `base_images`; with `--dev` it builds both shapes, handing the already-loaded root and config to `run_build` so nothing re-derives), `--dev`. `--gpu` does not exist on the verb: gpu is not runtime vocabulary, and a host that cannot run what it selected fails at container create. `COMPOSE_PROFILES`: shell env over `.env` (an explicitly empty shell assignment overrides a set `.env` value), comma-split, deduped, forwarded as explicit `--profile` flags (compose ignores the variable whenever any flag is present); unknown profile names refuse in the `Assembly` constructor, before the mirror probe and build. With a lock file present, `up` fail-closed probes every recorded digest — each image's index plus its platform manifests, and every chart entry (`docker buildx imagetools inspect`) — before bring-up, classifying stderr: only a registry 404 / manifest-unknown verdict is the not-mirrored error; unauthorized or transport failures report as probe failures carrying the underlying error text. The shell form renders only through `assembly.compose_command`, always with `--project-directory` at the invocation root and `.env` as `--env-file`, plus the synthesized lock env file as a second `--env-file` when a lock exists. |
| `verbs/down.py` | The `down` typer app. `down` keys on the project, not a file list: a name-only root file (written through `assembly.write_temp_compose_file`) plus `down --remove-orphans` removes every container the project ever created (any selection, any profile) without resolving a single include — an option's `:?err` env holes cannot break an open-mode teardown; both writes run inside `down`'s `ExitStack`, each pushing its own unwind, so a refusing run strands nothing in `/tmp`. A config-less or `services:`-less repo refuses loudly on both verbs through `assembly.require_compose_stack` — a builds-only, mirror-only, or k8s-only repo has no compose stack; the single-file default-file fallback is gone. `down` flags: `--volumes`/`-v`. |
| `assembly.py` | The resolve/render/validate stage: everything between the inputs and the docker compose invocation. `Assembly(root, config, stack, dev=False)` is the selected assembly as one record, rendered and proven — the constructor is one linear resolve→render→validate body, no per-stage helpers and no `try` clause (raises never sit inside a try; per-run file lifetimes ride the caller-owned `ExitStack`, never an exception handler): every environment read, selection derivation, document render, temp-file materialization, and compose-backed refusal runs exactly once in the constructor; each temp file pushes its own unwind onto the stack as it materializes, so a failure after the first write unwinds what was written — an invalid assembly strands nothing: the merged shell-over-`.env` view (`merged_environment` — authored placement: the merged environment view stays here, assembly state rather than a config derivation; the constructor requires `.env` — the friendly refusal — and merges shell env over file values, the `.env` parsing inlined; a missing `.env` reads as empty so score generation stays runnable on fresh checkouts), the `BUNDLES=` selection (the constructor applies the law; the riding entries, the option→group vocabulary, per-group choices, and the declaration-order entries flatten stay constructor-internal — the record exposes no selection projections, nothing prints them), the profiles, the auth-gated `forwarded` pair (derives `FORWARDED_PROTO`/`FORWARDED_PORT` from `PUBLIC_URL`, refusing when absent — only under a selected auth option), the `includes` list in `services:` declaration order with its missing-bundle-output refusal, the shared-service-name refusal over selected local outputs, the `output_services` set (the dev overlay's filter, read from the generated artifacts), and the riding routes, ports, and selected auth route. Rendering is member functions over the record, plain dicts out (no TypedDict layer: the emitted documents are write-only, built by comprehensions and dumped straight to YAML). The Caddyfile render is the edge's: one caddy site on the internal `:8443` (`EDGE_LISTEN_PORT`), each route a `handle` block (mutually exclusive; caddy sorts them longest-path-first, so declaration order cannot shadow — a test pins the rendering) — `handle_path` for `strip_prefix`, a bare `handle` for the `/*` catch-all, and `header_up X-Forwarded-Proto/Port` on the auth option's own route (derived from `PUBLIC_URL` exactly as the retired placeframe gateway entrypoint derived it); `raw:` route content rides verbatim under its path — the escape hatch for caddy behavior outside the dialect, a review flag rather than a feature — and the whole file rides as an inline `configs.content` with every `$` doubled (the `$`-doubling law). The dev overlay (under `dev=True`) renders: every assembly-defined service whose Dockerfile declares a genuine dev stage gets `image: {repository}/{service}:dev` plus the repo-root→`/app:ro` bind, and every selected workload's `dev-toggles` pairs — read through `WorkloadDocument`'s member and parsed through `config.parse_dev_toggles`, the one spelling law — become `${NAME:-default}` environment holes (spelling validated at generation; `up --dev` consumes; a present-but-malformed annotation refuses loudly — only the absent annotation and the outside-selected-outputs key skip); overlay keys outside the selected local outputs are filtered out (a stray key would add a half-defined service — deliberate and test-pinned), and `--dev` with no dev shape in the assembly refuses. The root renders before the overlay and the `-f` list (`compose_files`) carries root-then-overlay so the overlay overrides; both are per-run temp files whose unlinks ride the `ExitStack` (`write_temp_compose_file(stack, document, prefix)` writes and pushes in one step) — a successful handoff execs, the stack never unwinds, and the files ride out in the OS temp dir. The lock's env projection rides the same stack with the opposite failure policy: `write_lock_env_file(root, config, environment, stack)` materializes the selected-platform entries as a per-run second `--env-file` (None where no lock exists) and pushes `LockEnvUnwind` — under an exception it prints and keeps the file (`keep_lock_env_file`, the diagnostic of what the run saw), on a clean return it unlinks it, and an exec never runs it at all. Validation — the drift-impossible teeth — runs in the constructor over `compose_files` through compose's own resolution: whenever routes or ports exist, `docker compose config --services` must list every route upstream (the selected auth option's route rides the routes list by construction — its option is a selected entry, so it needs no separate check) and every port's owning service — the dev overlay's keys are a subset of the root's resolved services, so it changes nothing the check sees; whenever profiles are selected, `docker compose config --profiles` must list them. A selected bundle output that does not exist refuses naming generate-score; two selected local outputs sharing a service name refuse at construction only (selection-relative: each artifact alone is valid; the `edge`-reserved and dev-toggles spelling refusals live at generation). `compose_command(root, compose_files, *arguments, lock_env_file=)` is the one docker compose invocation spelling — `-f` per file, `--project-directory` at the root, `.env` as `--env-file`, the lock env file as a second `--env-file` when it exists, every dynamic interpolation shlex-quoted — shared by the constructor's validation calls and the verbs' handoffs. `write_temp_compose_file(stack, document, prefix)` is the per-run temp writer behind `compose_files` and `down`'s name-only root. `require_compose_stack(config)` is the no-compose-stack refusal both verbs share, returning the narrowed config so callers never re-assert it; `require_env_file(root)` the friendly `.env` refusal; `_split_names` (comma-split, strip, dedupe, drop empties) lives here. |
| `bake.py` | `run_build()` — the build pipeline behind the `build` verb — the bake render inlined in its body (the deterministic per-run bake file: authored key order, byte-identical for identical configs; tags and cache refs root under the destination when one is given, else the config's `repository` — one law for both push destinations; bake validates its own input by failing on it — no document model behind the render), with root/config injection defaults so `up --build` passes its already-loaded pair and nothing re-derives. ## The deployment-surface layer

Everything the deployment substrate (compose, k8s) needs to know about a workload that score's container model does not carry — host publishes, restart, gpu plumbing, scale-to-zero, healthcheck adaptation, consumer-supplied file content, dev toggles — lives in the **workload file** as `outernet.internal/*` annotations. `docker-devkit.yaml` never carries a per-workload runtime fact; it is build/render orchestration only. The devkit's shipped patch templates are the annotation reader: one annotation, one template, one behavior. The templates ship as package data under `src/docker_devkit/patch_templates/` (resolved via `importlib.resources`; a packaging test asserts every shipped template resolves) and register onto the devkit's own score-compose/score-k8s init invocations — consumer repos never author or declare one. Refusal laws (enums, form validation) live in devkit code (score's generation-time surface validation) because templates are data and cannot refuse. Score propagates `metadata.annotations` into both renderings, so the annotations ride the committed artifacts and the templates read them from the workload source — the truth the drift gate reproduces. Adding or renaming one of these annotations changes the committed artifacts: regeneration diff expectations must always include the annotation lines.

## Compose assembly and the `BUNDLES=` selection law

`up` derives the entire assembly from the consumer's root `docker-devkit.yaml` — one materialized root compose file per run, nothing hand-authored between the config and the running stack. Under `services:`, bare entries and group-level `routes:`/`ports:` ride unconditionally; only options are selectable, through `BUNDLES=` from the merged shell-over-`.env` view (the `COMPOSE_PROFILES` precedence; the `Assembly` constructor owns the law). The selection law: `BUNDLES=` names options only — a bare entry's name refuses as unselectable; at most one option per group (naming two refuses naming the group); zero options is legal exactly when riders or routes carry the assembly (omitting the auth pick is the anonymous edge — there is no explicit `open` entry); an options-only repo with an empty selection refuses; unknown names refuse loudly listing the vocabulary.

The materialized root carries the project `name:`, the `include:` list (remote refs verbatim, local outputs by absolute path, in `services:` declaration order), the emitted edge (iff any route rides), and parent-file port stanzas for every riding or selected `ports:` declaration. Compose merges parent ports into included services and honors `!reset` — a test against a version-pinned standalone compose binary pins both (the parent-over-include merge needs compose ≥ 2.40; 2.24–2.39 answer `conflicts with imported resource`). Validation runs in the `Assembly` constructor, whenever routes or ports exist, over the materialized file list (root plus dev overlay under `--dev`) through `docker compose config --services`: every route upstream (the auth option's rides the routes list by construction) and every port's owning service must resolve inside the selected assembly. A declared-but-empty compose assembly is unreachable — strictyaml refuses the empty spellings, and an options-only repo with nothing selected refuses at selection.

No `services:` section (or no config at all) → both verbs refuse loudly: a builds-only, mirror-only, or k8s-only repo has no compose stack, and there is no default-file fallback. `--compose-file` does not exist; the verbs own the compose invocation. `--dev` is opt-in — production-shaped bring-up is the default; dev mode is `.env` toggles + `build --dev` + `up --dev`.

`down` never reads the selection and never resolves an include: it materializes a name-only root and hands off `down --remove-orphans`, which removes every container labeled with the project — covering prior bring-ups under any selection and any profile, offline, with no env-hole interpolation of unselected options.

Profile-gated services are selected solely by `COMPOSE_PROFILES`; the verbs hold no built-in profile names. Gpu is not runtime vocabulary — no `--gpu` on `up`/`down`, no `{gpu}` file templating; a host that cannot run what it selected fails at container create.

## File and env conventions the commands assume

- `.env` (required by `up`/`down`, loaded through `assembly.py`) — carries `BUNDLES=` (the option selector), `COMPOSE_PROFILES`, `PLATFORM=` (the compose-edge platform selector in multi-platform repos), the dev-toggle overrides under `--dev`, and whatever variables the consumer's assembly interpolates — `GATEWAY_PORT` (the edge's published port), `PUBLIC_URL` (the auth edge derives the forwarded scheme/port from it), and the ports' `${…}` holes.
- `docker-devkit.lock` (repo root, committed, required exactly when `base_images` or `k8s.charts` are declared) — the declaration system's resolved state as structured YAML: an `images:` mapping name → `{index, platforms: {os/arch: reference}}` plus a `charts:` mapping name → flat digest-pinned reference, written only by the `lock` verb and `build`'s incremental freeze, never hand-authored. Env consumption is synthesized per-run at the edges — `up`/`down` attach the selected-platform projection as a second `--env-file`, bake reads the index projection as environment — so compose's native `--env-file` consumption at the `up` handoff survives the structured format.
- `.dockerignore` (where images are built locally) — allowlist that `config.py`'s service-sha machinery hashes over to compute per-service `tree-<hash>` tags. See "Docker build context" in `AGENTS-SHARED.md` for the allowlist rationale.

`build` injects the `tree-<hash>` tags of locally-built images into the environment rather than writing them anywhere; `up`/`down` do the same via `config.service_shas()`; `tree-tags` answers them on stdout. The lock stays a pure third-party pin file — a CI invariant forbids built-image digests in the committed, reviewed lock.

## Mirror namespace

Third-party images and charts are consumed through an org-owned mirror namespace (`ghcr.io/outernet-foundation/mirror/<upstream-host>/<path>…` — `DEFAULT_MIRROR_PREFIX`, overridable via the root `mirror_prefix` field) instead of pulling upstream registries directly: manifests at upstream get GC'd, and an upstream yank once broke external cloners — digest pins alone don't save you when the manifest is gone. Durability for strangers beats upstream egress: strangers, CI, and prod always pull the mirror. Populating it is CI's job, single writer — engineers never push to the org namespace, and error text must never teach them to (no "run this populate command" hints).

Declarations are upstream-native and the mirror-prefixed form is derived: `base_images` values and `k8s.charts` refs spell the upstream reference, and the prefix is the single place the namespace is named. `mirrored_ref(reference, prefix)` is the only join — it injects the prefix and rejects an already-prefixed reference (the double-prefix guard: drift toward the namespace is a loud error, never a silent skip); it lives in `config.py` beside `DEFAULT_MIRROR_PREFIX`, the prefix being a config fact. Under the override or the default:

- The lock records, per declared image, the mirror-prefixed reference resolved against upstream into the index digest plus one concrete platform-manifest digest per declared platform. Valid because `crane copy` produces byte-identical manifests — upstream and mirror digests are the same digest; a manifest re-wrap (`docker buildx imagetools`-shaped tooling) would change the top-level digest and break lock equality. This makes declare → re-lock walkable before CI has mirrored anything; lock entries are never hand-authored.
- `up` fails closed over the lock file: it probes every recorded digest (each image's index plus its platform manifests, and every chart entry — each mirror-prefixed by construction, the probe not gated on a `mirror_prefix` override); a missing mirror image is a hard `RuntimeError`, not a warning — people ignore warnings. There is no escape flag: a missing entry means the declaring change has not been through CI's mirror job yet, and the fix is to let it run. The probe's stderr is classified before an error is reported: only a registry 404 / manifest-unknown verdict gets the not-mirrored error; an unauthorized or transport failure (stale registry credentials, network, daemon down) is reported as a probe failure carrying the underlying error text, so a host-side problem can't masquerade as unmirrored CI debt.
- The `mirror` verb (the shared pinned crane installer, then a `crane digest` presence check per declared reference over every recorded digest — and `crane copy {ref} {prefix}/{ref}` for each one the mirror lacks, copying the whole index so the platform manifests ride along) uses bashrun + plain prints — it needs nothing from any runner floor. Presence is probed by the exact digests consumers pull, so once the mirror holds them, upstream retention is irrelevant: upstream GC of a manifest cannot break runs for bytes the mirror already owns, and upstream is consulted only to fetch what is missing. A probe that fails for any reason falls through to `crane copy`, which stays the loud gate — probe errors are never classified. Every declared reference is a target; nothing is filtered by prefix, so a drifted declaration cannot silently mirror zero, and the footer's copied/present split keeps a zero-copy run visible.

A `build --push` run leaves bake's `metadata.json` in the working directory (cwd-stable, dropped before the run) — the handoff the toolkit's build-workflow builds_ref step reads; the builds_ref step itself (distilling the metadata into digest-manifest shards) and all ORAS knowledge live toolkit-side in build-artifact-registry (org law), and the devkit carries no registry dependency and reads no `REGISTRY` facts. The shard keying law is stated in github-actions-toolkit's `AGENTS.md`. `docker-devkit.lock` stays in source control; local builds (no `--push`) never produce a handoff.

Lifecycle stays a separate package from codegen (client generation, datamodel generation, workspace locking) because their dependency surfaces are disjoint — bundling them would force a consumer that only brings a stack up to install `sqlacodegen`, `psycopg`, `datamodel-code-generator`.
